# User identity and operating modes

## Current implementation

- A Local Hub has a stable configured `hub_id` (`DBMAP_HUB_ID`, default `local-01`). The ID belongs to the Hub, not to a user. Nodes are identified by `node_id` in this Hub's database; there is no per-node `hub_id` column or hub hierarchy yet—this deployment is the association boundary.
- Device credentials stay separate. The bootstrap token is one-time and only authorizes `POST /api/v1/provision` while the node is `pending`, or after an admin opens recovery. Provisioning returns a distinct device API token once; the Hub stores `SHA-256` of it on `node_credentials` and the device stores the plaintext in NVS (`api_tok`). The MQTT password is still issued once into Mosquitto and NVS and is not an HTTP credential. Admin `POST /api/v1/nodes/{node_id}/device-api-token` rotates the HTTPS token without changing MQTT. `POST .../device-api-token/revoke` clears the hash. `POST .../recovery-provision` is the only way to provision again: it returns a new bootstrap token, and the following provision call rotates both the device API token and the MQTT password. A lost provision response cannot be retried with the consumed bootstrap token; open recovery again. Already-provisioned nodes keep working on MQTT with a null device API hash until an admin rotates a token into NVS. Plaintext tokens are not logged. `GET /api/v1/device/desired-firmware` identifies the node from the device API token and does not use OPA.
- The Hub API authenticates configured local admin and viewer bearer tokens. These are deployment credentials, not individual user accounts. OPA authorizes their roles and fails closed when it cannot decide.
- Desired state, reported state, observations, installation metadata, and ownership are stored separately. Ownership is an optional, admin-managed relationship with retained assignment history; ordinary-user sessions are not implemented yet.
- The `users` and `external_identities` tables provide the internal identity model. Admins can create, inspect, disable, and explicitly link these records. Admins and local viewers can read the user directory; the Users tab is read-only for viewers. These records are not used for login yet.
- Local Hub services, device communication, and local administration do not call GitHub. They use the local API, database, OPA, and MQTT services when internet access is unavailable.

## Operating modes

### Standard Local mode (current)

This is the only implemented mode. It requires no OAuth configuration or internet connection. The existing local admin/viewer credentials and CLI remain the access path. Missing GitHub configuration must not prevent the Hub from starting.

### Multi-user mode (future, opt-in)

This mode will add individual ordinary-user sessions through GitHub OAuth while reusing the existing Hub API, database, and device registry. It will not replace the local administrator path. Enabling it must be explicit in deployment configuration; until an enablement setting and OAuth routes exist, multi-user mode is unavailable.

GitHub availability is needed only to start a new sign-in or complete a callback. After sign-in, the Hub validates its own local session on API requests and does not call GitHub for every request. Use opaque, random, server-side sessions stored by hash with an expiry. Check that the user and linked identity remain active when accepting a session; disabling an account or identity then blocks its next request. Session expiry and logout are enforced locally.

## Internal users and external identities

- `users.user_id` is a stable UUID generated by dBmap. It remains unchanged if a display name or GitHub username changes.
- `external_identities` links a local user to a provider and a stable provider subject. For GitHub, use the numeric account ID, never the mutable username.
- A provider/subject pair can be linked to at most one internal user. A user may have multiple identities. Identity linking and unlinking require an authenticated, explicit action; names and email addresses never trigger automatic account merging.
- First-time account creation is closed by default. In the first multi-user release, a local admin must explicitly provision or invite an account before a GitHub identity can be linked. OAuth sign-in never grants administrator rights.
- Disabling a user blocks that user's access but preserves the user, identity links, and any future ownership/history records. Disabling an identity prevents sign-in through that provider and preserves its link for audit and safe recovery. Do not hard-delete these records through ordinary account management.
- Do not retain GitHub access tokens. The initial login needs the provider identity only; request no provider scopes beyond those needed to identify the account.
- Each Local Hub owns its own user and identity records. A matching GitHub identity on another Hub does not imply a shared account or synchronized permissions.

## Separation from devices and installation

Hub identity, node identity, user identity, ownership, and installation remain distinct:

| Concept | Current representation | Relationship |
| --- | --- | --- |
| Local Hub | `DBMAP_HUB_ID` / `settings.hub_id` (status API `hub_id`) | One configured identity for this Hub; not a database user or node ID |
| Device | `nodes.node_id` in the Local Hub database | Stable across user changes and installation updates; there is no per-node Hub association field yet |
| Installation | `installation_metadata.node_id` | Current site/location facts keyed to the device; no owner relationship |
| Ownership | `device_ownership` assignment rows | Optional owner relationship keyed to stable device and user IDs; reassignment retains prior rows |
| User | `users.user_id` | Stable dBmap UUID; may be assigned as owner by the local administrator |
| Login identity | `external_identities.identity_id`, provider, provider subject | Explicitly linked to one internal user |

Provisioning a device does not require a user. Relocation or ownership changes do not replace the device ID or delete observations. Ownership is assigned explicitly by a local administrator; it is never inferred from who signs in or provisions the device. An owner may read detailed device status after ordinary-user sessions are implemented. Owners cannot edit installation or configuration; those operations remain local-admin-only.

## Schema and migration status

The `users`, `external_identities`, and `device_ownership` tables are additive. Startup currently uses SQLAlchemy `create_all` to create missing tables; ownership rows are initially empty, and startup does not rewrite node, installation, or observation records. There is no Alembic migration framework in this service yet. Any future schema change that alters existing records must include an explicit, backed-up migration and rollback/recovery instructions.

The admin provisioning/linking API and Users tab exist, but the tables do not make multi-user login available. Before enabling it, implement and test the session store, API authorization for individual users, OAuth callback protections, and opt-in deployment configuration. Keep the existing local admin credential usable if GitHub or the internet is unavailable.
